# BiQuad Monitor — professional app and delivery plan

Approved implementation plan · 8 October 2026 · Preserved baseline: 0.1.4

**Recommendation:** evolve the working native app into a compact cellular measurement instrument with an optional larger antenna-analysis workspace. Build it with SwiftUI, AppKit and Swift Charts. Use Codex, VS Code and GitHub for an automated, evidence-backed delivery workflow inspired by Factory.

**Confirmed by the user:** Codex + GitHub, inspired by Factory. Factory subscriptions, Droids and a migration to another coding environment are not part of this proposal.

The owner approved this plan before implementation. The public MIT source baseline and professional preview are now being implemented. This document preserves the research and planned acceptance criteria; see the current README and compatibility guide for delivery status. The companion [visual concept](2026-10-08-pro-concept.png) ([editable SVG](2026-10-08-pro-concept.svg)) is an original static illustration with synthetic readings, not a working app or a verified native screenshot.

## 2. Product direction and visual design

Factory's overview combines a delivery-stage view with health, coverage and run metrics, and currently labels the product Private Preview. We will use that lifecycle concept for development. The app's appearance takes inspiration from its restrained dark panels and orange accents. [Factory overview](https://docs.factory.com/software-factory/overview), [Factory website](https://factory.com/).

WiFi Explorer Pro contributes a different useful idea: configurable tables, inspectors, saved views and analysis graphs. Its spectrum features depend on appropriate data sources/hardware; the Cudy signal endpoint does not supply an RF spectrum scan. [WiFi Explorer Pro](https://www.intuitibits.com/products/wifiexplorerpro3/).

### Three surfaces, one application

| Surface | Intended use | Proposed behaviour |
| --- | --- | --- |
| Menu bar | Glance while working or moving an antenna | Full metric names, current band, explicit freshness/status |
| Compact tuner | Watch measurements beside another app | Roughly 400 × 480 points; large selected metric, four-value strip, short chart, trial controls; optional pin above other windows |
| Analysis workspace | Review experiments and longer trends | Roughly 1100 × 740 points initially; sidebar, measurement table, synchronized charts and collapsible inspector |

The default menu format will be exactly:

```text
LTE BAND 3 | SINR 8 | RSRQ −9 | RSRP −96 | RSSI 23
```

Values and band come from the router. Formatting uses the proper minus sign, retains meaningful decimals and shows `—` for unknown fields. The menu has Full, Compact and Custom presets; Full is the requested default. A preview lets the user choose which metrics fit the available menu space. We will test narrow displays and the MacBook notch; opening the app from Finder must always recover the main window if the menu item is hidden. The tooltip and compact panel explain units and the last successful reading. Demo, stale data and no cellular service are explicit states.

### Workspace navigation

- **Live:** radio measurements, detailed cellular table, timeline and event markers.
- **Antenna Lab:** record a position, allow it to settle, compare trials and inspect variability.
- **Sessions:** reopen, filter, annotate, compare and export saved measurements.
- **Diagnostics:** connection stages, safe errors, adapter/firmware capabilities and optional link checks.
- **Settings:** router profile, polling, menu contents, appearance, history retention, alerts and startup.

### Visual system

Use warm charcoal backgrounds, fine separators, restrained orange selection/action accents and legible off-white text. Proposed starting tokens: background `#111110`, surface `#191817`, elevated surface `#22201E`, border `#3A3734`, primary text `#F3F1ED`, secondary text `#B2ABA4`, accent `#EF7A3C`. Validate actual contrast in context, including disabled states.

SF Pro handles navigation and labels; tabular SF Mono numerals align readings and tables. Use 4/8-point spacing, moderate corner radii, native window chrome and keyboard behaviour. Charts use distinct colours plus labels/line styles. Large empty cards, decorative gauges and continuous animations should not dominate the workspace. Dark, Light and System modes must all remain usable.

At narrower widths, collapse the inspector first and then the sidebar; preserve chart labels and scrolling. Keep the existing window-boundary recovery and test monitor disconnection, display scaling and reopening. Provide accessible chart summaries, keyboard navigation, visible focus and reduced-motion behaviour. Native Swift Charts supports integration with SwiftUI and accessibility. [Swift Charts](https://developer.apple.com/documentation/charts), [Apple chart guidance](https://developer.apple.com/design/human-interface-guidelines/charts).

## 3. Features that earn their place

### First professional release: required

| Feature | Concrete result |
| --- | --- |
| Reliable four-metric monitoring | SINR/RSRQ in dB, RSRP in dBm, RSSI in verified router units; missing values never become zero |
| Context beside the readings | Carrier/RAT, band and cell; add PCI, channel bandwidth and connection duration only after validating their actual responses |
| Time-based charts | 1/5/30-minute, 1-hour and session views; real timestamps, crosshair and visible missing-data gaps |
| Comparable chart scales | Shared scale when comparing the same metric across trials; units remain separate across different metrics |
| Event timeline | Band/cell change, connection loss, recovery, pause, trial start and user notes |
| Durable sessions | Survive restart; samples retain session/trial IDs, units, timestamps and data-quality state |
| Antenna comparison | Guided settle/record/compare flow, reference trial, delta and variability; explicit comparability warnings |
| Exports | CSV and versioned JSON containing units, timestamps, gaps/events and trial identity; preview privacy options |
| Clear recovery | Controlled retry, sleep/wake handling, actionable authentication/transport errors and a reconnect action |
| Useful controls | Pause/resume collection, annotate, select time range, compare trials and configure display |

RSSI `23` is currently a raw router index. It must not be relabelled as `23 dBm`. Unit interpretation becomes adapter metadata rather than a general guess from the sign. Unknown sentinel values and unsupported fields get explicit quality states.

The Mac-to-router Wi-Fi signal and router-to-Three cellular signal represent separate links. An optional Wi-Fi panel can later show local signal/noise/channel when available, clearly labelled **Mac Wi-Fi link**. It must not replace or get mixed into the cellular metrics. [Apple CoreWLAN interface](https://developer.apple.com/documentation/corewlan/cwinterface).

### Antenna Lab: a useful experiment, not just moving numbers

1. Create a session with a descriptive antenna setup. Optional fields: antenna A/B, orientation, tilt, cable description and notes. Orientation is manually entered unless an actual sensor is introduced.
2. Record a baseline with a configurable settling period and measurement period; suggested starting defaults are 60 seconds settling and 120 seconds recording. These are workflow defaults, not a guarantee of statistical sufficiency.
3. Change one physical variable and start a new trial. Previous trials remain saved.
4. Show sample count, duration, coverage, median, interquartile range and 10th/90th percentiles for each metric. Show raw traces so statistics can be checked.
5. Compare only matching band/cell/unit segments by default. A change of cell or band splits the segment and warns the user; missing identity means comparability is unknown.
6. Permit an A/B/A repeat to see whether the baseline drifted. Describe results as observed differences. Network load and radio conditions prevent the app from proving antenna gain or throughput from signal readings alone.

Suggested later additions: optional audio feedback while aiming, a compact comparison report, threshold alerts with persistence/hysteresis and cooldown, saved workspace layouts, and user-triggered latency checks. Audio and notifications are opt-in. Probe targets, interval and measured protocol must be visible; connection latency is labelled separately from radio quality. Bulk speed tests should be explicit actions with a data-use estimate.

### Deferred until the core is accepted

Multi-router simultaneous monitoring, additional Cudy models, Wi-Fi scanning, tower maps, spectrum analysis, per-antenna/MIMO readings, AT command controls, band locking and firmware changes require separate capability evidence. The present endpoint does not establish those capabilities. The first public release can honestly support the tested LT500 V2 firmware while providing an adapter interface for future models.

## 4. Technical architecture

Keep the existing Swift investment and working Cudy login flow. Use a small Xcode application/UI-test target around reusable Swift package modules; continue editing in VS Code and building through command-line tools. Retain macOS 13 as the provisional minimum. Audit API availability and test the minimum OS before advertising support; do not silently raise it for a convenient API.

```text
AppKit windows/menu + SwiftUI views + Swift Charts
                       │
             Presentation state (MainActor)
                       │
      Monitoring engine / session coordinator
             │                         │
    Cudy adapter + transport     Session store (SQLite)
             │                         │
       Router on the LAN       Trials / samples / events

       Pure models, statistics and export formatting
                 shared by app and tests
```

Proposed responsibilities:

- **SignalCore:** typed measurements, units, data quality, statistics and comparison rules. Keep independent of UI and transport.
- **RouterAdapters:** Cudy authentication, strict local address validation, bounded responses, parsing and capability reporting. Tests inject transport, clock and fixtures.
- **Monitoring:** asynchronous polling, cancellation, retry policy, freshness and cellular state. Move parsing and disk work off the UI actor.
- **SessionStore:** system SQLite with parameterized operations, a serialized background writer, versioned migrations and transactional imports/exports. No third-party database runtime is needed.
- **App:** menu formatter, compact tuner, workspace, settings and accessible chart presentation.

Retain the verified endpoint `/cgi-bin/luci/admin/network/gcom/status?detail=1&iface=4g`. Add new fields using minimal sanitized fixtures, not whole router pages or backups. Preserve same-origin redirects, ephemeral cookies and normal TLS certificate validation. Any plain-HTTP allowance stays constrained by the router transport; audit the existing broad ATS setting during packaging changes.

Model router connectivity/authentication, data freshness and cellular connection as separate dimensions. Keep last-good values with their timestamp, but suppress current-reading claims when stale. Default polling remains five seconds with one in-flight request. Proposed stale threshold: three missed expected intervals. Retry transient failures with bounded backoff up to 60 seconds; recover promptly after wake/network return. An authentication failure permits one controlled session renewal when the user has enabled saved credentials, then asks for sign-in. Never retry a rejected password indefinitely.

Use stable UUIDs for router profile, session and trial. Store original metric value/unit, observation time, validity, adapter version and contextual band/cell with each sample. Store gaps/events explicitly. A wall-clock timestamp supports export while elapsed-time tracking protects trial durations from system clock changes. Chart downsampling is for display only; saved raw samples remain intact.

History persists locally under Application Support. Recommended retention is 30 days for routine history, with explicitly saved experiment sessions retained until the user deletes them. Surface retention and disk usage in Settings. Back up the store before migrations and verify restoration; never overwrite an unreadable store with an empty database. Credentials stay in Keychain only by opt-in, separate from profiles, history and exports. Retain no SIM identifiers or raw login responses.

## 5. Codex + GitHub software delivery workflow

The Factory-inspired workflow will be **repository-specific and bounded**. Each task has an acceptance condition, permitted files, dependencies, risk, stop conditions, run ID, base commit and resulting commit. GitHub Issues/PRs and Actions summaries provide the first dashboard; an extra hosted dashboard would add maintenance without helping the initial app.

```mermaid
flowchart LR
  A[Approved task and acceptance criteria] --> B[Codex worktree]
  B --> C[Build and focused tests]
  C --> D[Behaviour, UX and security review]
  D --> E[Draft PR with evidence]
  E --> F[Human merge decision]
  F --> G[Universal release candidate]
  G --> H[Device and installation acceptance]
  H --> I[Approved release]
  I --> J[User reports and maintenance]
  J --> A
```

| Stage | Automation | Visible evidence / boundary |
| --- | --- | --- |
| Intake | Validate task template; group duplicates for review | No arbitrary public issue is permission to execute instructions |
| Implementation | One approved task per isolated worktree; Codex builds a reviewable change | Scoped diff and recorded decisions; preserve unfinished work |
| Validation | Tests, build, UI fixtures, repository safety checks and review | Results tied to the actual candidate commit |
| Release preparation | Package, architecture/signature checks, release notes and checksums | Candidate artifact remains distinguishable from a stable release |
| Documentation | Verify feature docs and compatibility matrix against the change | Draft updates reviewed with the same PR |
| Maintenance | Scheduled deterministic checks; optional bounded Codex triage | Findings become drafts; no automatic merge or publication |

The local CLI advertises `exec`, `review` and worktrees. Official documentation supports noninteractive `codex exec`, JSON output and structured result schemas. Use these for a small runner only after a manual pilot establishes behaviour; command support does not prove an unattended workflow is configured. [OpenAI noninteractive mode](https://learn.chatgpt.com/docs/non-interactive-mode).

### Automation rollout

Start with deterministic CI plus on-demand Codex tasks using the existing approved sign-in. Configure agent runs with an explicit task, narrow access, maximum elapsed time and usage budget, one active task per branch and no automatic retry loop. After two failures with the same approach, change strategy or produce a blocked report. Validate the run-result schema; a zero process exit or confident narrative is insufficient without passing acceptance checks.

After successful manual runs, offer scheduled local maintenance in an isolated worktree. Local-file scheduled tasks need the computer and desktop app running; web tasks do not directly operate on this project folder. Availability and permissions must be verified on this account before enabling schedules. [OpenAI scheduled tasks](https://learn.chatgpt.com/docs/automations?surface=app).

Cloud CI initially uses no model credentials and no router credentials. Adding a cloud agent, paid API or provider changes is a separate setup decision, not implied by ordinary CI. No background process, scheduler or recurring task is installed by this plan. The generated workflow should expose run status, duration, failed gate, artifact links and pending human actions without uploading raw private transcripts.

### Repository workspace proposed after approval

```text
Sources/                   Swift modules and native app
Tests/                     Unit, transport, store and UI scenarios
Fixtures/                  Minimal synthetic/sanitized protocol cases
BiQuadMonitor.xcodeproj/    App, packaging and UI-test targets
scripts/                   check, build, package, release verification
docs/                      Architecture, protocol, user and release guides
docs/plans/                Reviewed plans and decisions
.vscode/                   Build/test tasks without personal settings
.github/workflows/         CI, candidate packaging, approved release
.github/ISSUE_TEMPLATE/     Bug / feature / adapter-support reports
```

Keep workflow scripts small and callable both locally and in CI. Add one project guide that points to actual commands and boundaries; avoid duplicating personal policies or generating a large agent framework for this small app.

## 6. Git and public GitHub preparation

Proposed repository: **`subkoks/BiQuadMonitor`**, public, SSH remote `git@github.com:subkoks/BiQuadMonitor.git`. Public description: “Native macOS cellular signal monitor and antenna experiment workspace for supported Cudy routers.” MIT is the recommended license for the original app code, subject to the user's approval. Confirm ownership and dependency/assets provenance before applying it.

Sequence:

1. Preserve the working source and 0.1.4 app as a private recovery baseline. Record only safe filenames/metadata; the router backup is unnecessary for publication.
2. Extend exclusions for app bundles, build outputs, recovery, router backups, downloaded firmware/installers, private captures/logs, credentials and local profiles. Preserve these files locally.
3. Initialize local Git with `main`. Explicitly stage reviewed source, tests, build files and safe documentation. Inspect staged content and scan it with redacted output. Check archive contents before upload. Never use a blanket initial `git add .`.
4. Make the source baseline commit, then use a feature branch for the redesign. Keep commit messages scoped and conventional. Avoid a history import that could contain old debug credentials.
5. Create/push the approved public repository only after the publication manifest passes. Audit this plan and all screenshots before publication too: use synthetic examples, omit account-specific notes and private workstation details from public-facing docs.
6. Add README, license, contribution/security guidance, issue/PR templates, compatibility matrix and release instructions. State independent-project status and actual tested router/OS/architecture coverage.
7. Enable supported secret scanning/push protection and required passing CI checks. Require the actual check names after workflows have run; verify the resulting rules rather than assuming the settings took effect.

GitHub secret scanning is useful but cannot be relied on to recognize an arbitrary router password or encrypted backup. The source allowlist and exclusion check remain required. [GitHub secret scanning](https://docs.github.com/en/code-security/concepts/secret-security/about-alerts).

PR workflows use minimal token permissions, SHA-pinned actions, timeouts, cancellation of superseded runs and no release secrets. Forked/untrusted code never runs on the user's Mac or LAN through a public self-hosted runner. Signing runs only in a separate approved release job from trusted code. [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use).

## 7. Intel, Apple Silicon and public releases

**Primary download:** one Universal `BiQuad Monitor.app` containing `x86_64` and `arm64`. Separate architecture archives can be optional downloads if size justifies them; avoid making users select a CPU architecture unnecessarily. Apple documents that Intel can build a Universal binary but cannot execute the arm64 slice. Native execution must therefore be verified separately. [Apple Universal binaries](https://developer.apple.com/documentation/apple-silicon/building-a-universal-macos-binary).

Use matching SDK/toolchain settings to archive both architectures, verify Mach-O slices and embedded components, then sign the final bundle. Keep the application filename and bundle identity stable across releases, with version numbers in bundle metadata and archive names. Review the existing `local.blackterminal.BiQuadMonitor` identifier before choosing any migration; changing it can affect saved settings and identity.

Proposed CI matrix uses explicit Intel and arm64 runner labels, currently including `macos-15-intel` and `macos-15`. Pin a compatible Xcode version available on both and revalidate labels at implementation time. Current standard public-repository hosted runners are documented as free; larger runners and paid agent services are outside this assumption. [GitHub hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).

Checks cover native tests on both CPU types, release builds, fixture UI flows, bundle metadata, architecture presence, prohibited-file scanning and a candidate package. Add Swift/Python/Actions CodeQL analysis after verifying the selected toolchain is supported; do not call an unexecuted scan a security pass. [GitHub CodeQL](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-code-scanning).

For straightforward public installation, use Developer ID signing, Hardened Runtime, a secure timestamp, notarization and a stapled ticket; inspect notary logs and test the final downloaded artifact with Gatekeeper. Availability of an Apple Developer identity is unverified; no signing credentials were read. Local ad hoc builds remain useful for development but are not the public-distribution acceptance result. [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

**Permission acceptance matters:** Apple documents different Local Network treatment for command-line programs launched from Terminal and GUI apps, and notes that multiple app copies and unstable identity can complicate permission tracking. Test first launch from Finder, denial/recovery and a normal update using a stable installation. CLI live tests alone do not prove this. No firewall shutdown or global privacy bypass belongs in onboarding. [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).

Cloud runners validate simulated router behaviour; they cannot reach the user's private router. Intel and Apple Silicon test reports must distinguish unit/UI fixtures from physical-router acceptance. If a required platform or minimum OS cannot be tested, mark it unverified and hold the corresponding support claim.

## 8. Implementation phases and acceptance

Each phase is independently reviewable. The sequence protects a working app while improving the measurement model before adding sophisticated views. Relative sizes describe scope, not promised delivery dates.

| Phase | Deliverable | Acceptance gate | Rollback / dependency |
| --- | --- | --- | --- |
| 1 — Foundation (small) | Private recovery baseline, source-only Git setup, build/test commands, publication manifest and initial CI | Current 27 tests pass; a clean checkout builds; archives contain no private/third-party files | Keep 0.1.4 runnable; publish only the reviewed manifest |
| 2 — Menu and connection core (medium) | Exact full labels, presets, explicit freshness/cellular states, retry/cancellation and modular transport | Formatter edge cases; no overlapping polls; missing/expired/offline cases; Finder launch and live comparison | Separate commit/build; preserve login and existing settings |
| 3 — Session data (medium) | SQLite store, stable trials, events, retention, CSV/JSON | Restart/crash recovery, migration restore, correct per-trial exports and unit-safe comparisons | Back up before migration; previous app can run without modifying new store |
| 4 — Professional workspace (large) | Compact tuner, Live/Sessions/Diagnostics views, linked charts, settings and theme | Deterministic visual states, keyboard/VoiceOver, real-time gaps, small/multiple displays, responsive resizing | Retain compact working surface while workspace is developed |
| 5 — Antenna Lab (medium) | Settle/record/compare flow, segment checks, statistics, notes and comparison export | Known synthetic trials give exact results; changed band/cell cannot imply improvement; cancelled trials remain coherent | Additive session fields and feature-level rollback |
| 6 — Universal release candidate (medium) | Intel/arm64 CI, packaging, signing/notarization when provisioned, clean-install instructions | Candidate tied to tested source; both architectures; final bundle install; required live and soak checks | Keep last accepted package and tested data backup; no stable label before gates pass |
| 7 — Maintenance automation and refinements (small initially) | On-demand Codex runner, evidence dashboard, then opted-in schedules; audio/alerts/layout presets in separate changes | Deliberate test failures stop the run; budgets/stop controls work; no unintended pushes/releases | Disable a workflow/schedule without affecting app operation |

Initial proof after approval: phases 1–2 should produce a usable small update before the broader interface lands. Phases 3–6 complete the professional baseline. Deterministic CI starts early; recurring agent automation is enabled only after its manual pilot is trustworthy.

### What “working” must mean

- Fresh router readings agree with the browser's same-time observations within normal polling timing, including missing/disconnected states. Polling does not alter router settings.
- Eight-hour soak shows no accumulating memory/request leak; a shorter development run is recorded separately and does not substitute for the soak.
- Simulated network loss, session expiry, sleep/wake and malformed responses recover or clearly request action. No stale data is labelled live.
- Reopening the app restores saved sessions and settings; trial boundaries, timestamps and exports remain correct.
- Both architecture test jobs pass. Packaged GUI and minimum-OS evidence are listed separately.
- Menu, compact and workspace views remain reachable after display changes; keyboard and accessibility checks cover real flows.
- Release package comes from the checked commit, contains only intended files and passes the distribution checks appropriate to its label.

Provisional performance targets on the user's Intel Mac at five-second polling: under 1% average background CPU while idle, under 150 MB resident memory with a typical session open, and UI actions responding within roughly 100 ms. First profile the current and proposed builds, record workload/machine details and adjust justified targets before treating them as gates. These are goals, not measured results.

## 9. Three review passes over this plan

| Review | Main challenge | Resolution in the proposal |
| --- | --- | --- |
| Product and UX | More features could overwhelm a small menu app | Separate compact and analysis surfaces; prioritize antenna decisions and readable metrics |

These are explicit review passes, not a claim that three independent agents audited the implementation.
